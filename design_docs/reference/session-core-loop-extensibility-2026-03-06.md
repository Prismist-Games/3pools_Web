我从结构层面看这个问题。先把核心循环抽象一下：

**花金币 → 从池中获取物品 → 把物品匹配到订单需求 → 获得奖励**

这个循环里，物品是中心节点 — 它连接了"获取"和"交付"两端。那我们看物品到底承载了什么：

一个物品有两个有意义的属性：**名字**（用来匹配订单）和 **品质**（用来计算价值）。除此之外，物品没有任何功能性。西瓜和柠檬的区别，只在于订单要的是哪个名字。它们不"做"任何事。

换句话说 — **物品是匹配用的 token，不是有功能的游戏元素。**

这就导致了一个结构性问题：

### 你能加的内容，和它们产生的效果

| 加什么 | 实际产生的变化 |
|--------|----------------|
| 新物品（第21种） | 多一个名字可以匹配，策略不变 |
| 新物品池（第6个池子） | 更多名字，同上 |
| 新品质等级 | 数值多一个梯度，决策结构不变 |
| 新词缀 | **这个确实能改变决策**，但它只作用于"抽取交易"这一个表面 |
| 新订单类型 | 只要还是"要求名字+品质"，就只是不同的匹配目标 |
| 新技能 | 大多是数值修正器（更多金币、更好概率），不改变你"做"什么 |

### 对比：为什么有些游戏加内容就有新玩法

像 Slay the Spire 或 Balatro，每加一张卡，它和已有的卡之间会产生**组合交互** — 新卡改变了你能做的事，打开了新的策略路径。这些游戏的内容之间有**密集的交互网络**。

三池物语目前的交互网络是**稀疏的**：
- 物品和物品之间没有交互（合成只是品质+1，不产生新功能）
- 物品和词缀之间没有交互
- 订单和订单之间没有交互
- 技能之间基本没有交互

**加一个新元素，它和已有元素之间几乎不产生新连接。** 这就是"封闭"感的结构根源。

### 根本原因

不是内容不够多，而是 **物品缺乏功能性身份**。它们只是匹配 token。在一个 token-matching 系统里，内容扩展的天花板天然就低 — 因为新 token 不会和旧 token 产生有意义的交互。

## 分析总结

**表层感受**：加新内容很难产生有意义的新玩法，设计空间感觉窄。

**结构根源**：游戏的内容元素之间缺乏组合性交互。物品是纯匹配 token（只有名字+品质），词缀只作用于孤立的抽取交易，订单只是匹配目标。加新元素 = 线性增长，不是指数增长。

**本质约束**：目前系统中没有任何一个内容维度具备"A + B 产生 A 和 B 单独都没有的效果"这个性质。这是扩展性天花板低的统一原因。

**方向**：需要在循环中引入某种**上下文相关的、组合性的价值** — 让"我从池子里拿到的东西"的意义，取决于"我已经有什么"或"当前的游戏状态是什么"。

---

有一个需要留意的**张力**：

如果引入组合性交互，游戏的重心可能会从**池子选择时刻**滑向**库存管理/搭配组合**。对你来说，核心体验是"在池子前做选择"，那扩展性的方案就需要让组合性**反哺池子选择的深度** — 让你在选池子时要考虑的东西更多更有趣，而不是让选池子变得无所谓、真正的游戏在背包里发生。

## Step 1: 寻找方向

### 定位隐藏前提

问题所在的系统：核心循环（池子 → 物品 → 订单）。围绕这个系统，当前设计不自觉地默认了以下前提：

| 前提 | 内容 | 与问题的关系 |
|------|------|-------------|
| **物品是惰性的** | 物品没有功能性，不"做"任何事，只是匹配用的 token（名字+品质） | **直接相关** — 这是内容无法组合交互的核心原因 |
| **物品是独立的** | 库存中的物品互不影响，每个物品的价值只取决于自身和订单的匹配关系 | **直接相关** — 没有物品间关系，就没有组合空间 |
| **订单是物品的唯一去处** | 物品存在的意义就是提交给订单，别无他用（回收只是弃牌） | **相关** — 单一用途意味着新物品只增加匹配变体 |
| **抽取是自包含交易** | 金币进、物品出，不与库存状态或其他游戏状态产生交互 | **间接相关** — 限制了词缀的扩展空间 |

### 挑战前提，生成方向

**方向 A：让物品获得组合性属性**

挑战前提："物品是惰性的 / 物品是独立的"。

如果物品拥有超越名字+品质的属性（标签、效果、特性），那么物品之间就能产生组合交互。每加一个新物品，它不是"又一个名字"，而是交互网络中的一个新节点，和已有物品产生新连接。

**如何反哺池子选择**："这个池子的物品有属性 X，和我库存里已有的属性 Y 能产生组合效果" — 选池子时要考虑的维度变多了，决策更丰富。

**风险**：如果物品属性太复杂，玩家在池子选择时刻的认知负担过重，评估变得不可能。游戏重心可能从"选池子"滑向"管背包"。

---

**方向 B：增加第二个系统循环，为池子选择创造变化的上下文**

挑战前提："订单是物品的唯一去处"。

不改变物品本身，而是在核心循环之外增加一个与之交互的系统层。让同样的池子选择在不同时期服务于不同的目的 — 你不只是在为当前订单抽取，你的抽取还影响着某个更大的、持续演变的东西。

**如何反哺池子选择**：同一个池子在不同上下文中价值不同。"现在抽水果池不只是因为订单要水果，还因为水果推进了我的 XX 进度。" 选池子的理由从单维度（订单匹配）变成多维度。

**风险**：如果元系统和核心循环整合不深，会感觉是"打工 → 攒资源 → 推进度"的割裂结构。核心循环可能沦为服务元系统的磨损。

---

**两个方向的本质区别**：
- **A 改变你在评估什么** — 物品有了更多维度，同一个决策点的信息更丰富
- **B 改变你为什么在抽** — 不同的目标在不同时间改变对同一个池子的评估

两者不互斥，但各自独立也能成立。**你倾向哪个方向？** 还是想先讨论再决定？

## Step 2: Decompose

从"物品获得组合性属性"走到"核心玩法具备内容扩展性"，需要同时满足哪些条件？

**条件 1：物品具备超越名字+品质的功能性属性**
物品需要携带某种属性，使得不同物品在gameplay层面上是"不一样的东西"，而不只是不同的名字。这是一切的基础 — 没有属性就没有交互。

**条件 2：属性之间能产生组合效果**
属性本身不够 — 属性 A 和属性 B 放在一起要能产生 A 和 B 单独都没有的效果。这是组合性交互的定义，也是扩展性的来源。没有这个，新属性只是线性增加，和现在加新物品名字没有本质区别。

**条件 3：组合效果在池子选择时刻可评估**
玩家在决定"抽哪个池子"的时候，要能考虑到组合效果。如果组合效果只在提交订单时才显现，池子选择仍然只是匹配订单需求，没有被丰富。组合效果必须向上游传导，影响抽取决策。

**条件 4：认知负担与策略深度的平衡**
组合性不能让决策变得不可计算。玩家需要能"看懂"组合关系，做出有理由的选择，而不是面对无法评估的复杂度后放弃思考、随便选。这是轻中度策略游戏的定位要求。

**条件 5：属性系统本身是可扩展的**
新属性能被加入而不破坏已有属性的交互结构。如果每加一个新属性都要手动设计它和所有已有属性的交互，那扩展性只是被转移到了设计工作量上，没有被真正解决。需要某种结构性的方式让新内容自然地产生交互。

### 依赖关系

```
条件1 ──→ 条件2 ──→ 条件3
  │                    │
  └──→ 条件5          条件4
```

- 条件 2 依赖条件 1（没属性就没组合）
- 条件 3 依赖条件 2（没组合效果就没什么可在池子选择时评估的）
- 条件 4 和条件 3 存在**张力** — 组合越丰富，认知负担越大
- 条件 5 依赖条件 1 的设计方式 — 属性的结构决定了扩展是容易还是困难

### 完备性检查

如果 1-5 全部完美满足：物品有属性，属性间有组合效果，组合效果影响池子选择，认知负担可控，系统可扩展 — 扩展性问题是否解决？

我认为是的。唯一可能遗漏的是：**组合效果需要有足够的gameplay后果**（影响得分、影响经济、影响后续选择等），否则组合只是装饰性的。但这其实包含在条件 2 的"产生效果"中 — "效果"本身就意味着有gameplay后果。

## Step 3: Design

### Candidate A：词缀烙印（Affix Imprint）

**核心改动**：物品永久携带它被抽出时池子的词缀作为"烙印"。烙印成为物品的第三个属性维度（名字、品质、烙印）。

**运作方式**：

1. **获得烙印**：从带"精准"词缀的池子抽出的西瓜 = 一个携带"精准"烙印的西瓜。烙印跟随物品一生。

2. **订单烙印条件**：订单可以附带烙印相关的加分条件。例如："提交的物品烙印全部相同：+X分"，"提交的物品包含3种不同烙印：+Y分"。这不替代原有的名字+品质需求，而是额外的奖励层。

3. **合成交互**：同名同品质但不同烙印的物品合成，结果可能与同烙印合成不同（例如：跨烙印合成有额外效果，或保留其中一个烙印由玩家选择）。

**为什么用这个方案**：它把已有的词缀系统从"影响抽取那一刻"延伸到"影响物品的整个生命周期"。不是新加一个系统，而是让现有系统的影响力贯穿更远。

**条件覆盖**：

| 条件 | 如何满足 |
|------|---------|
| 1. 物品有新属性 | 烙印 = 第三维度 |
| 2. 属性间组合效果 | 不同烙印组合满足不同订单条件 / 影响合成结果 |
| 3. 池子选择时可评估 | 池子的词缀已经可见 → 烙印结果确定 → "这个池子给我的物品会带'精准'烙印，我需要再凑一个'精准'来满足订单加分条件" |
| 4. 认知负担可控 | 零新信息源 — 词缀已经在池子上显示。唯一新概念是"词缀留在物品上"。交互规则通过订单条件自然呈现 |
| 5. 系统可扩展 | 每个新词缀自动成为新烙印 → 自动和所有已有烙印产生组合可能 → 无需手动设计每对交互 |

**风险**：
- 词缀是随机分配给池子的，玩家不能选择"我想要精准词缀的池子出现"。如果策略过度依赖特定烙印组合，随机性可能让人沮丧。但这和游戏"不确定中做策略选择"的核心身份一致 — 你适应当前出现的东西，而不是执行固定计划。
- 需要确认：烙印条件加分的幅度要足够有意义，让玩家真的care，但不能大到"没凑齐烙印就不值得提交"。

---

### Candidate B：物品特质词汇表（Item Traits）

**核心改动**：每个物品在定义时被赋予 1 个特质，特质来自一个共享词汇表（约 6-8 个特质）。特质之间有交互规则。

**运作方式**：

1. **特质分配**：每种物品有固定特质。西瓜 ="清爽"，红宝石 ="炽热"，黑胡椒 ="辛辣"。玩家逐渐学会哪个物品有什么特质。

2. **特质交互规则**：特定特质对在一起产生效果。"清爽+炽热 = 淬炼（提交时加分）"，"辛辣+辛辣 = 浓烈（合成时品质额外+1）"。规则表是预定义的。

3. **影响订单和合成**：和 Candidate A 类似，但交互来源于物品的固有特质而非抽取上下文。

**条件覆盖**：

| 条件 | 如何满足 |
|------|---------|
| 1. 物品有新属性 | 特质 = 固有标签 |
| 2. 属性间组合效果 | 特质对触发效果 |
| 3. 池子选择时可评估 | 知道池子里有什么物品 → 知道这些物品有什么特质 → 可以评估 |
| 4. 认知负担可控 | ⚠️ 需要记忆：20个物品各自的特质 + 特质交互表。比 A 的认知负担更高 |
| 5. 系统可扩展 | ⚠️ 半扩展：加新特质需要手动定义它和已有特质的交互规则。不是自动生成的 |

**风险**：
- 条件 5 满足得不够好 — 扩展性被转移到了"设计特质交互表"的工作量上
- 认知负担较高 — 玩家需要记忆两层映射（物品→特质，特质→交互）
- 更多的前期设计和平衡工作

---

### 对比

| 维度 | A: 词缀烙印 | B: 物品特质 |
|------|------------|-----------|
| 新概念数量 | 1个（烙印留在物品上） | 2个（特质 + 交互表） |
| 利用已有设计 | 高 — 延伸词缀系统 | 低 — 全新系统 |
| 条件5（扩展性） | 强 — 新词缀自动扩展 | 弱 — 需手动设计交互 |
| 设计者控制力 | 较低 — 组合是涌现的 | 较高 — 交互是预设的 |
| 认知负担 | 低 | 中 |
| 实现工作量 | 较小 | 较大 |

**被排除的方向**：库存空间位置交互（物品根据摆放位置产生组合）— 在池子选择时刻无法评估，违反条件 3，排除。

## Step 2: Decompose

从"库存成为主动gameplay空间"走到"核心玩法具备内容扩展性"，需要满足什么条件？

**条件 1：库存中存在有意义的物品间操作**
超越当前的"同名同品质合成"。玩家能对库存中的物品做更多事，且这些操作的结果是有意义的（影响得分、经济、或后续选择）。

**条件 2：操作选择取决于上下文**
同样的两个物品，在不同的库存状态 / 订单需求 / 游戏阶段下，最优操作不同。这样操作才是"决策"而不是"流程" — 玩家需要根据当前情况判断做什么。

**条件 3：操作规则是结构性的，不是逐对定义的**
规则基于物品已有属性（池子类别、品质、名字）的关系来运作，而不是"西瓜+红宝石=特殊效果"这种手动定义。这样新物品加入时自动参与已有规则，不需要额外设计每一对交互。这是扩展性的关键。

**条件 4：操作结果反哺池子选择**
库存里能做的事影响玩家"从哪个池子抽"的决策。"我库存里有水果，如果抽一个矿石就能做 XX" → 池子选择因为库存操作而变得更丰富。如果库存操作和池子选择脱节，核心体验没有被深化。

**条件 5：认知负担在轻中度范围内**
操作规则数量少（可以用手指数），容易学习，不需要查表。玩家通过几次尝试就能掌握"什么和什么能做什么"。

### 依赖关系

```
条件3 ──→ 条件1 ──→ 条件2
  │                    │
  │         条件4 ←────┘
  │
  └──→ 条件5（与条件1、3存在张力：操作越丰富，规则越多，认知越重）
```

- 条件 1 依赖条件 3：操作的设计方式决定了它们是否有意义
- 条件 2 依赖条件 1：有操作才有上下文敏感性
- 条件 4 依赖条件 2：操作选择有上下文差异，才会影响"我需要什么"→ 影响池子选择
- 条件 5 与条件 1、3 存在张力：规则太多或太复杂就会超出重量级

### 完备性检查

如果 1-5 全部满足：库存有结构性的、上下文敏感的操作，反哺池子选择，认知可控 — 扩展性问题解决了吗？

我认为是的。新物品通过结构性规则自动和已有物品产生操作可能（条件3），这些操作影响策略（条件2、4），且不爆炸复杂度（条件5）。

## Step 3: Design

### 候选方案：结构性组合系统

**核心改动**：任何两个**同品质**的物品都可以组合。组合结果由两个物品的**结构关系**（名字、池子类别）决定。

三条规则：

| 关系 | 操作 | 结果 | 直觉 |
|------|------|------|------|
| 同名 + 同品质 | **合成**（已有） | 同名，品质+1 | 一样的东西叠在一起 → 变更好 |
| 同池不同名 + 同品质 | **精选** | 玩家从该池所有物品中选一个，保持品质 | 同类的东西拆开重组 → 选你想要的 |
| 不同池 + 同品质 | **融合** | 品质+1，随机获得其中一个池的物品 | 不同的东西碰撞 → 升级但不可控 |

**它创造的决策举例**：

库存里有：普通西瓜、普通柠檬。订单需要：普通苹果。
→ **精选**：把西瓜+柠檬组合 → 选苹果 → 完成订单。代价是 2 换 1。
→ 或者：留着两个分别看后续订单能不能用？

库存里有：普通西瓜、普通红宝石。订单需要稀有物品。
→ **融合**：品质+1 得到稀有，但名字随机（可能是水果也可能是宝石）。赌一把还是等更好的机会？

库存里有：两个普通西瓜。
→ **合成**：直接升品质且保留名字 — 最好的结果，但条件也最难凑。
→ 或者两个西瓜分别能满足两个订单？那别合。

**条件覆盖**：

| 条件 | 如何满足 |
|------|---------|
| 1. 有意义的物品间操作 | 3 种组合，各有不同结果和适用场景 |
| 2. 操作选择取决于上下文 | 同样两个水果，订单不同 → 精选 vs 保留的决策不同 |
| 3. 规则是结构性的 | 基于同名/同池/跨池关系，新物品自动参与，零额外设计 |
| 4. 反哺池子选择 | "我有一个普通水果，再抽一个任意普通水果就能精选出我要的" → 水果池变得更有吸引力；"我有一个普通矿石，抽任意其他池的普通物品就能融合升品质" → 更多池子变得有用 |
| 5. 认知负担 | 3 条规则，基于直觉关系（同类→选、异类→升），不需查表 |

**这个系统解决原始问题的方式**：

目前抽到"不需要的物品"= 浪费（只能回收换点金币）。有了组合系统后，"不需要的物品"有了新价值 — 作为组合材料。池子选择从"这个池子有我直接需要的吗"变成"这个池子的物品能和我已有的做什么" — 评估维度更丰富。

每加一个新物品，它自动成为所有同品质物品的潜在组合对象。扩展性来自新物品 × 结构规则 = 新可能，不需要手动设计交互。

**风险**：
- **精选可能太强**：2 个同池物品 → 精确拿到你要的，可能让订单完成太容易。可能需要某种成本（消耗金币？品质降一级？）来平衡
- **融合的随机性**：品质+1 但名字随机，可能让人沮丧。但这和游戏的"不确定中做选择"身份一致
- **同品质约束**：只有同品质才能组合，这意味着品质不同的物品无法互动。这是有意为之的简化（减少规则数），但也意味着库存中品质参差的物品之间仍然是"死"的

这些路径要求的思考方式是真正不同的 — 定向匹配是精确采购，凑组是拼图补缺，转化链是规划流水线，投资是长期押注，投机是即时判断。

游戏不需要全部包含 — 2-3 种就够。但需要至少有一种和"定向匹配"（当前唯一路径）质性不同的路径并存。

## 完整的结构洞察

### 原始问题
核心玩法感觉封闭，缺乏内容扩展性。

### 根因链
1. 所有决策共享同一个优化轴（金币→分数效率）
2. 因为物品只有一个去处（订单），只有一种转化路径（匹配→得分）
3. 因为经济循环是单向管道：金币→物品→分数
4. 所以无论内容怎么变（新物品、新词缀、新订单），玩家的思考方式不变

### 结构方向
将经济循环从**单路径管道**改为**多路径网络**。需要三个结构性质同时成立：

1. **物品有多个去处，回报不可互相折算** — 不同去处给玩家的东西是质性不同的，不能折算成同一标准来比较
2. **至少一条反馈回路** — 某个去处的回报改变了池子/抽取端的体验，创造路径依赖
3. **多条质性不同的转化路径，且不同状态下不同路径占优** — 不需要多个目标，但需要多种达成方式，游戏状态决定哪条路径当前最有价值

### 核心骨架（不变的）
货币 → 从池子抽取 → 获得物品 → 提交物品。这个动作循环不变。

### 扩展性来源
**"去处"本身就是可扩展的内容层。** 每个去处由"接受什么物品 + 返回什么"定义，基于物品的结构属性（池子类别、品质、名字）运作。加一个新去处 = 加一种新转化路径，自动和所有已有物品产生交互。加一个新物品 = 自动参与所有已有去处的规则。

## Step 3: Design

### 三个提交去处

```
              ┌── 订单 → 货币（维持经济循环）
货币 → 池子 → 物品 ─┼── 池子投资 → 池子演化（反馈到源头）
              └── 阶段推进 → 进入下一阶段（推进目标）
```

**去处 1：订单 → 货币**

基本延续现有订单机制。提交匹配物品，获得货币。货币用于从池子抽取。这是经济循环的**燃料站** — 不赚燃料就没法继续抽取。

回报：货币（让你继续玩下去）。

**去处 2：池子投资 → 池子演化**

将物品提交回池子，池子发生变化 — 品质分布改善、解锁新物品、抽取成本降低、或其他演化效果。

回报：改变未来从这个池子能获得什么（反馈回路）。

这创造路径依赖：投资水果池 → 水果池变强 → 你的这一局变成水果主导的游戏。另一局投资宝石池 → 完全不同的局面。

**去处 3：阶段推进 → 进入下一阶段**

提交满足特定条件的物品来推进到下一个游戏阶段。现有设计中已经有4个阶段，各有不同的机制规则（波动性、专业化、熵/衰减）。目前阶段推进是自动的 — 改为**玩家主动推进**。

回报：游戏规则改变（进入新阶段 = 新的游戏状态）。

这就是替代"分数"的目标：通过所有阶段。不是累积一个数字，而是推进一段旅程。

---

### 三者之间的张力

每个物品只能提交给一个去处。三个去处竞争同一批物品：

| 时刻 | 张力 |
|------|------|
| 货币不足 | 必须交订单换燃料，即使物品用于投资或推进更有价值 |
| 池子很弱 | 投资池子改善未来抽取，但牺牲了当下的货币和推进 |
| 接近阶段门槛 | 冲刺推进，但可能掏空经济 |
| 进入新阶段后 | 规则变了，之前的投资方向可能需要调整 |

这些不是同一种计算 — "赚燃料"是维持生存，"投资池子"是塑造未来，"推进阶段"是战略时机判断。三种不同的思考方式。

---

### 条件覆盖

| 条件 | 如何满足 |
|------|---------|
| 1. 多个去处，回报不可折算 | 货币、池子演化、阶段推进 — 三者无法用同一标准衡量 |
| 2. 反馈回路 | 池子投资直接改变池子产出 |
| 3. 多路径，状态相关 | 经济紧张→订单优先；池子弱→投资优先；时机成熟→推进优先。不同阶段规则不同，进一步改变最优路径 |

### 扩展性

- **新池子演化路径**：新的投资方向 = 新的长期策略。自动和所有物品交互。
- **新阶段**：新的游戏规则 = 新的战略环境。改变三个去处的相对价值。
- **新订单类型**：不同的燃料获取方式 = 不同的短期策略。
- **新物品/池子**：自动参与所有三个去处。

### 风险

- **池子投资回报不好感知**："我投了3个物品进去，池子变好了吗？" 如果变化太渐进或不可见，玩家不会觉得投资有意义。需要让演化效果**立即可感知**。
- **阶段推进时机**：如果新阶段严格更难，玩家可能永远不想推进（一直在第一阶段刷）。需要某种机制让停滞不前有代价，或让新阶段有足够吸引力。
- **三个去处的平衡**：如果某个去处在所有情况下都明显最优，多路径网络就名存实亡。需要通过游戏状态的动态变化来保持张力。
- **阶段推进作为目标**：如果"通过所有阶段"感觉像是被迫推进而非主动选择，体验会变成打工。阶段推进的条件和节奏需要让玩家感觉是**战略选择**，不是**任务清单**。

## 方案：城镇建造

选城镇建造是因为：实现最简单（不需要战斗结算逻辑），天然可组合，扩展性好，和现有的物品池子类别有直接映射。

### 核心结构

```
货币 → 池子 → 物品 ─┬── 提交订单 → 货币（维持经济）
                     └── 建造/升级建筑 → 建筑产出效果（游戏目标）
```

### 建筑系统

**5个建筑槽位**，每个槽位可以建造一栋建筑。

**建造方式**：提交物品到空槽位。物品的池子类别决定建筑类型，物品的品质决定建筑等级。后续可以继续提交物品来升级。

**5种建筑类型**（对应5个池子类别）：

| 池子 | 建筑 | 效果 |
|------|------|------|
| 水果 | 果园 | 每回合产出额外货币 |
| 蔬菜 | 农田 | 每回合产出额外货币（类型不同，可与果园互补） |
| 矿石 | 矿场 | 降低抽取费用 |
| 宝石 | 工坊 | 提升抽取品质概率 |
| 香料 | 商铺 | 提升订单奖励 |

每栋建筑效果随等级线性增强。

**胜利条件**：所有建筑的等级总和达到目标值。或者：建筑每回合产出"繁荣点"，繁荣点累计达到目标。

### 为什么这创造不同的体验

**建筑组合决定策略方向**：
- 重矿场+工坊 → 便宜抽取+高品质，但繁荣产出慢
- 重果园+农田 → 经济富裕但池子不强
- 平衡发展 → 稳健但没有爆发

**每一局的池子随机性驱动不同的建造路径**：
- 这一局宝石池频繁出现 → 自然走工坊路线
- 那一局水果+矿石多 → 果园+矿场路线

**核心张力**：每个物品要么交订单换货币（短期），要么投入建筑（长期）。不同时刻最优选择不同。

### 扩展性

- **新建筑类型**：新效果 = 新策略方向。自动和所有物品交互。
- **建筑协同**：后期可加"相邻建筑加成"或"特定组合触发额外效果"。每个新协同 = 新策略。
- **建筑升级树**：建筑升到一定等级可以分支进化（矿场→深矿/露天矿，效果不同）。
- **新池子**：自动产生新建筑类型。

### 实现复杂度：低

需要的新组件：
- 建筑槽位 UI（5个卡片/格子）
- 建筑数据定义（类型 × 等级 × 效果值）
- "提交物品到建筑"交互（类似现有的提交订单）
- 每回合效果结算（遍历建筑，应用效果）
- 胜利条件检查

现有系统不需要大改 — 建筑系统是平行添加的，通过"提交物品"接口和资源产出系统对接。

## 修正方案：以消费层为核心的城镇建造

### 核心转变

### 结构

**项目目录**：游戏有一个丰富的项目库。每个项目定义：
- **需求**：物品组合（"2个普通水果 + 1个稀有矿石"）
- **奖励**：多样化 — 货币、永久加成、解锁新项目、特殊物品、新池子类型...
- **解锁条件**：完成哪些前置项目后才可见

```
项目A（基础农场）
  需求：普通水果×2 + 普通蔬菜×1
  奖励：每回合+2货币，解锁项目D和项目E
       │
  ┌────┴────┐
项目D（温室）    项目E（果酒坊）
  需求：稀有水果×1    需求：普通水果×3 + 普通香料×1
  + 普通矿石×2      奖励：大量货币，解锁项目K
  奖励：解锁稀有蔬菜池
```

### 为什么这次不一样

**内容承载在消费端**：每个新项目 = 一个新的物品组合需求 = 一种新的池子选择逻辑。加50个项目 = 50种不同的"我在凑什么"。

**项目之间的分支创造策略多样性**：走农业路线和走工业路线需要完全不同的物品，导致完全不同的池子选择模式。不同的路线不是"同一种优化的不同参数"，而是"我在玩一个不同的游戏"。

**奖励多样性创造反馈**：有的项目奖励货币（维持经济），有的解锁新项目（开路），有的提供永久加成（改变游戏参数），有的解锁新池子内容（改变资源端）。不同奖励类型让项目选择不可互相折算。

**扩展性是自然的**：设计一个新项目 = 写一条数据（需求+奖励+解锁）。不需要新机制、新代码。内容可以无限扩展，每条新内容自动和池子系统交互。

### 胜利条件

可以是：
- 建成特定标志性项目（项目树末端的大工程）
- 城镇达到某个综合发展程度
- 灵活定义 — 不同场景/关卡可以有不同目标

### 实现复杂度

项目系统本质上是**数据驱动**的：

```javascript
{
  id: "greenhouse",
  requires: [
    { pool: "fruit", minRarity: "rare", count: 1 },
    { pool: "mineral", minRarity: "common", count: 2 }
  ],
  rewards: { currency: 10, unlock: ["project_K"], permanent: { newPoolItems: ["rare_vegetable_set"] } },
  prerequisite: ["basic_farm"]
}
```

核心代码：需求检查 + 奖励发放 + 解锁追踪。现有的订单提交逻辑可以直接复用扩展。

## 简化

我上面提的项目树（前置条件、解锁链、分支路径）太重了。对一个3人团队来说，设计大量关联项目本身就是巨大的内容工作量，而且前期必须设计好整棵树才能开始。

更简单的模型：**蓝图池**。

游戏有一个蓝图库。每回合，从库中呈现若干可建造的蓝图（类似当前池子从池子库中随机呈现）。每张蓝图 = 一组物品组合需求 + 一个奖励。你选择追求哪个蓝图。

不需要前置关系。不需要科技树。蓝图的出现可以是随机的、基于当前局面的、或混合的。新蓝图 = 新数据条目，不需要设计整棵树的关联。

和项目树的区别：项目树是预设路径（战略规划感），蓝图池是动态机会（战术适应感）。后者更简单，也更贴合当前游戏"面对随机呈现的选择做决策"的核心体验。

## 嵌入当前骨架

当前每回合的结构：

```
看池子 → 花货币抽取 → 物品进库存 → 提交物品到订单 → 获得货币+分数
```

我不应该在旁边"加一个建筑系统"。更好的做法是：**扩展"提交"这一步能做的事情**。

当前：提交目标只有一种类型（订单 = 匹配物品换货币+分数）。

修改后：提交目标有多种类型，共享同一个界面和操作逻辑（"提交物品组合 → 获得奖励"），但需求和奖励各不相同。

```
                    ┌── 贸易单（提交物品 → 货币）
看池子 → 花货币抽取 → 物品 ─┼── 建造蓝图（提交物品 → 建筑落成，产生持续效果）
                    └── 其他类型（后续可扩展）
```

**关键简化**：不是加新系统，而是让现有的"订单"机制变成一个**通用提交框架**，不同类型的提交目标都通过同一套接口运作。

建筑建成后，它的效果可以影响任何东西 — 每回合产出额外货币、改变蓝图池的构成、为特定池子类别增加物品、改变抽取参数... 这些都是奖励的具体实例，不需要新机制。

**扩展方式**：加一种新的提交目标类型 = 内容扩展。加新蓝图 = 内容扩展。都是数据，不是新机制。

## 替换失败条件

当前："金币归零 → 游戏结束"。问题：
- 造成死亡螺旋（越穷越难翻盘）
- 让所有决策都围绕"别破产"这一个焦虑
- 和"建造/发展"的体验基调冲突

**替换方案：回合制 + 固定收入**

- 游戏有固定回合数（比如20回合）。到期结束，不会中途死亡。
- 每回合自动获得基础货币收入。抽取花费货币，但永远不会归零到无法继续。
- 建筑可以增加每回合收入（造得好 → 更多收入 → 更多抽取机会 → 正向循环）。

这样：
- **没有死亡螺旋** — 你永远能继续玩
- **有资源压力** — 每回合的货币是有限的，你必须在"抽更多"和"省着用"之间取舍
- **建筑创造正反馈** — 早期投资建筑 → 中后期收入更高 → 更多操作空间
- **终局有明确节奏** — 知道还剩几回合，后期决策和前期自然不同（前期投资，后期冲刺）

胜利条件变成：在有限回合内，通过建造和发展，达成特定目标（总建筑等级、特定标志建筑、综合发展度...具体形态后续定）。

### 整合后的每回合流程

```
1. 获得货币（基础收入 + 建筑加成）
2. 池子呈现（3个池子 + 若干可用蓝图/贸易单）
3. 抽取阶段：花货币从池子抽取物品
4. 提交阶段：将物品提交给贸易单（换货币）或蓝图（造建筑）
5. 结算：建筑效果生效，回合推进
```

骨架没变（货币→池子→物品→提交），但提交端变厚了，失败条件消除了，游戏节奏由回合制控制。
