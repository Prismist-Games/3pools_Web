## 系统设计意图

### 局内：节目（奖品墙）

**行列抽取**：策略选择的核心载体——同一格子有两条触达路径（所在行或所在列），玩家在食材需求、命中概率、厄运风险、附带收益之间做权衡。

**食材 → 订单**：食材是过程性资源，订单是把"食材"变成"更好品质食材"的转化器。80 种食材按市场类型分割，每次选市场都在选择"本回合能获得哪类食材"。

**品质系统**：为同一食材类型增加深度维度。玩家在"足量低品质"和"少量高品质"之间做选择。合成机制提供了一条从低到高的提升路径。

**市场类型**：提供局内变化——每次选择 3 选 1 时，要决定优先哪类食材，根据当前订单需求和菜品目标做决策。当前市场信息完全可见，策略信息透明。

**厄运**：游戏的核心压力源。每回合 +1 危险，厄运结算格（抢菜人）以 15% 概率出现，平均每面墙约 2.4 格。Push-your-luck 的紧迫感来自厄运网格越来越脏。

### 局外：厨房

**核心定位**：情境设置器，不是第二个游戏。给局内提供目标和意义。

**槽位制**：直观且支持"妥协"体验——食材匹配度有梯度，高品质+精准食材和低匹配度通配食材是两条路线。

**派遣五边形**：把"成功率"几何化、可读化。

### 人气值

**双重身份**：HP（活下去）+ 经济引擎（提升做菜上限）。

## 当前设计重点

1. **食材/订单/品质三角** — 三者的平衡感是否让玩家感到选择有意义
2. **市场决策深度** — 3 选 1 时的策略信息是否足够；是否需要在"信息透明"和"push-your-luck"之间找平衡
3. **合成价值感** — 合成 2→1 的效率感，何时值得合成 vs 直接提交
4. **厄运密度** — 15% 每格约每墙 2.4 格抢菜人，是否合适
5. **局外回路接线** — 派遣判定与厨房做菜结算打通，跑通完整 day 循环
6. **人气值公式定型** — 涨跌曲线、归零失败、经济联动
7. **菜品扩展** — 当前 DISHES 数量较少，需要更多菜品支撑天数
8. **订单刷新来源** — 当前无格子产生刷新次数，需设计

- **legacy 配置未清理**：`constants.js` 中 v1 系统全保留，约 600+ 行死代码

- **modifier 逻辑死代码**：约 400 行 modifier 处理代码因 wallType id 不匹配而永不触发
- **i18n 覆盖不全**：新增的食材/品质/市场相关字符串部分缺英文翻译
- **getClusterMembers deprecated 但未删**：matrixHelpers.js 中簇 BFS 函数仍存在，等待彻底清理
- **订单刷新次数来源缺失**：刷新次数从 0 开始，无格子来源，玩家无法主动刷单（规划中）
