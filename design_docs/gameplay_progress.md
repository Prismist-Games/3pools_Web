# 玩法设计进度 - LAN 多人原型

最后更新：2026-05-08

本文档同步当前 worktree 的玩法设计状态。当前分支的重点不是继续扩展单人撤离版，而是验证“多人竞争 + 独立抽奖 + 共享订单争夺”的核心体验是否成立。

---

## 1. 当前核心命题

把原本“一个玩家面对 3 个池子和订单做抽奖决策”的结构，改造成 2-4 人同桌竞争：

- 所有人面对同样的订单与同样的 3 个奖池。
- 每个人根据自己的背包、金币、订单接近度独立选择奖池。
- 抽奖互不影响，但结果公开。
- 订单是共享目标，一个人完成后其他人失去该目标。

这个方向比单人版多了一层“读人”和“抢窗口”的张力：玩家不仅要算自己抽哪个池子，也要看别人是否即将完成某个订单，以及是否值得抢先投入资源。

---

## 2. 已确定的多人规则决策

| 系统 | 当前决策 | 设计原因 |
| --- | --- | --- |
| 玩家数 | 2-4 人；1 人不能开始 | 第一版验证真实多人竞争，避免单人流程污染判断 |
| 订单 | 所有人共享同一批 3 个订单 | 把原单人目标转化为可争夺公共目标 |
| 订单刷新 | 完成后立即替换；手动刷新移除 | 避免刷新成为低交互的个人修正按钮 |
| 奖池 | 每轮共享同样 3 个奖池 | 保证玩家在同一个战术环境中做不同判断 |
| 抽奖 | 每人独立选择，所有可行动玩家选完后同时开奖 | 保留随机惊喜，同时减少轮流等待 |
| 背包 | 私人背包，但完全公开可见 | 支撑玩家判断别人离订单还有多近 |
| 背包满 | 个人事件，不阻塞其他玩家 | 避免一个人的整理时间拖慢全桌节奏 |
| 交互词缀 | 选择内容只对本人可见，金币开奖时才扣 | 避免精准/有的放矢/以旧换新提前泄露意图 |
| 淘汰 | 金币无法支付任何可用奖池时停止抽奖 | 形成自然终局，不需要撤离系统 |
| 结算 | 所有人停止抽奖后比分 | 第一版目标清晰，便于验证节奏和竞争感 |

## 3. 系统状态地图

### 奖池

状态：核心系统，已接入多人。

当前奖池仍使用原来的 5 个物品池和 7 个词缀。多人版的关键变化不是奖池内容，而是“同一轮三个奖池对所有人公开”。这让奖池从单人优化题变成公共战术题：同一个“药物 + 精准”可能对 A 是补订单，对 B 是阻止 A 的抢单尝试，对 C 则完全不值钱。

风险：如果订单可读性不足，玩家会退回只看自己背包的单人式决策。因此 UI 里的奖池 hover、订单胶囊高亮、背包订单角标不是装饰，而是核心可读性设施。

### 订单

状态：核心系统，已改为共享争夺。

当前共享订单承担三重职责：

- 给抽奖选择提供目标；
- 制造玩家之间的竞争；
- 驱动分数增长。

已移除手动刷新。这个决定是正确的：多人中手动刷新会把公共市场变成个人修正工具，并且会带来“谁有权刷新共享订单”的规则负担。

当前风险：订单提交是即时服务器先到先得。若玩家频繁出现“我也能交但被抢”的体验，可能需要未来加入更明确的提交窗口、同时结算、锁单、或竞速提示。第一版先保留简单实现，用实测判断问题强度。

### 背包

状态：核心系统，已接入多人公开可见。

自己的背包是主要操作区，保留整理、合成、回收、待处理替换/回收。其他玩家背包作为次级信息区展示，不与自己的完整操作区并列。

背包公开的好处是让订单争夺变得可判断；代价是降低秘密信息。当前原型选择“完全公开”，因为第一阶段要验证公共订单争夺是否足够有趣，优先保证信息可读。

### 金币

状态：局内寿命资源。

多人版中金币比单人版更像“本局行动寿命”。玩家花金币抽奖，通过回收获得少量续航；当无法支付任何可用奖池时停止抽奖。这个结构让终局自然发生。

风险：如果回收收益过高，玩家会通过清背包拖长局面；如果过低，则背包管理只剩止损。当前沿用品质回收值，等待实测。

### 词缀

状态：核心系统，效果沿用，信息展示规则已调整。

交互词缀在多人里有信息泄露风险。例如玩家正在选择“有的放矢”时，如果其他人能看到金币提前变化或选择状态，就可能推断其意图。当前实现把交互状态只发给本人，金币也只在开奖时扣除。

### 撤离 / 离开关卡

状态：多人版本移除。

移除原因不是该系统无价值，而是它与当前多人验证目标冲突。多人第一版需要一个清晰终局：所有人金钱耗尽后比订单得分。撤离会引入风险结算、提前离场、节奏分叉等额外问题，暂时不进入本轮验证。

### 技能、工具物品、阶段系统

状态：多人版本未启用。

这些系统在旧单人原型中有定义，但当前多人服务器使用 `hasSkill = false`，也没有工具物品掉落流程。它们暂时属于“可复用素材”，不是当前多人规则的一部分。

## 4. 当前体验判断

### 已经变强的部分

- 订单从个人目标变成公共战场，天然增强互动。
- 同一组奖池让玩家可以比较彼此判断，开奖结果也更有桌面感。
- 公开背包让“他快完成了”这件事可见，形成抢单压力。
- 背包满不阻塞他人，是多人节奏上的必要改动。

### 仍需验证的部分

- 订单争夺是否会变成纯手速，还是主要来自前几轮抽奖规划。
- 公背包是否让思考量过载，特别是 4 人局。
- 玩家停止抽奖后是否还有观看乐趣。
- 30 金币是否让局长合适；不同玩家被淘汰时间差是否过大。
- 回收是否会让落后玩家有可感知的追赶选择。
- 共享订单立即刷新是否会让后手玩家感觉随机被惩罚。

---

## 5. UI/信息可读性要求

多人版不能只“显示数据”，必须帮助玩家快速读局面。当前需要保留并继续维护以下可读性功能：

- 奖池 hover 时，高亮该池可能产出的物品对应的订单需求胶囊。
- 背包物品 hover 时，高亮对应订单需求。
- 自己和他人的背包物品都显示订单匹配角标。
- 绿色角标表示该物品品质已经满足当前某个订单需求。
- 灰色角标表示只满足名称但品质不足。
- 最近开奖结果显示每个人抽到了什么。
- 交互词缀选择 UI 只出现在本人界面。

---

## 6. 技术原型边界

当前多人实现是 LAN 快速验证原型，不是线上产品架构：

- 单服务器单房间。
- 无账号、无房间码、无持久化。
- 无断线重连。
- 无观战模式。
- 无服务端防作弊模型，只做基本权威状态处理。
- 无自动化测试套件，依赖构建和脚本模拟验证。

这些限制是可接受的，因为当前目标是验证玩法，不是交付正式网络游戏。

---

## 7. 下一轮值得重点观察的问题

1. 2 人局和 4 人局的订单争夺是否是同一种体验，还是需要不同订单数量/金币参数。
2. 玩家是否真的会看别人背包，还是只看自己的匹配角标。
3. 被抢订单后，玩家是否觉得“这是我能预判的竞争”，还是觉得“系统突然拿走了目标”。
4. 玩家停止抽奖后的等待是否太长。
5. 是否需要把订单提交也改成回合化或窗口化，避免即时点击竞争。
6. 是否需要加入轻量的“锁定订单/预约订单/共同竞价”机制，但这应在实测证明必要后再做。
