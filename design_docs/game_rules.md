## 游戏概述

**主题**：人如何与不确定性共处。主角的餐厅濒临倒闭，电视烹饪节目给了他一个翻盘的机会——每天参加节目搜集食材，回家做菜挽救人气值。

**核心张力**：
- 局内（节目）：贴纸需求 vs 厄运风险，行列选择的策略博弈
- 局外（厨房）：做菜评分 → 人气涨跌 → 影响后续天数

**胜利条件**：当前原型阶段沿用 v2 设定——3 场（3 天）累计 ≥ 30 分。终局"评审 Boss"机制规划中。

## 大局结构（Day 循环）

每"天"= 一次节目搜打撤 + 一次回家做菜结算。

```
[Day N 开始]
   │
   ▼
看到今天的菜品要求（菜名 + 槽位结构 + 五维目标）
   │
   ▼
进入节目（局内）
  - 选择奖品墙
  - 抽贴纸 / 完成订单 / 获得食材
  - 决定撤离时机
   │
   ▼
回家做菜（局外）
  - 把食材填入菜品槽位
  - 派遣判定五维评分
  - 人气值涨跌
   │
   ▼
[Day N+1] ── 直到达成胜利条件
```

代码中：`dayNumber` 即天数计数；`expeditionScores` 累积各天得分；`phase` 状态机驱动 `pre_game → setup → wall_choice → wall_reveal → drawing → between_turns → restaurant → cook_result → pre_game`（下一天）。

## 开局组建（Setup）

每天 `startGame` 进入 `setup` phase，玩家先做两个动作再进入第一面墙：

1. **今日菜单揭晓**：全屏黑屏浮层展示今日菜品图标 + 名称，点击任意位置继续（`RoundTransition` 组件）
2. **5 次"二选一"订单**：依次弹出 5 个二选一 picker 填充货架。不能跳过——必须选满 5 单才能进入抽墙

### 配置

| 项目 | 值 |
|------|------|
| `SETUP_CONFIG.pickCount` | 5 |
| 每对候选订单数 | 2 |
| 初始货架订单数 | 0（由 setup 填满到 5） |
| 初始刷新次数 | 0（由订单格 +1 累积） |
| 是否可跳过 | 否 |

### 设计意图

- 让每天的第一回合前就已经有明确的订单组合方向，而不是被系统随机撒 5 单
- setup 期间中央常驻 DishCard 显示菜品和槽位需求，玩家可据此倾向性地挑订单
- 同时修复"首墙生成时货架尚无订单"的副作用——首墙生成时货架已填满 5 单

## 局内：节目（奖品墙）

### 奖品墙基本结构

- **大小**：4×4（代码 `MATRIX_CONFIG.gridSize: 4`）
- 每回合一面墙，回合内不补充
- 每次抽取选择**行**或**列**，从该行/列里随机抽中 1 个格子
- 每个格子都是独立的 1×1 实体（已移除 polyomino / groupId 机制）。**相邻同 id 贴纸会自动结成簇，抽中时整簇消除** —— 详见[簇系统](#簇cluster系统)

### 格子类型与每格生成概率（Procedural 墙）

墙生成现在是**单轮每格 roll**（不再是旧的 Phase 1 正态分布 + Phase 2 累积概率）。每个格子按以下概率序排：

| 类型 | 每格概率 | 抽中效果 |
|------|---------|----------|
| 💰 金币格 | 6% | 获得 1-2 金币 |
| 📋 订单格 | 4% | 刷新次数 +1（上限 5）；不再直接生成订单 |
| 🎁 食材格 | 2% | 获得局外食材（按稀有度 40/30/20/10 加权） |
| 💣 炸弹格 | 4% | 爆炸摧毁周围 8 格 |
| 💀 厄运结算格 | 5% | 触发结算 |
| ⬆️ 厄运升级格 | 5% | 厄运等级 +1 |
| 🌽 膨化格 | 0% | 仅由特定 modifier（如祝福愈合）产生；相邻抽取加成 +1 |
| 贴纸格 | 余下空格 | 整簇消除产出 |

累计非贴纸概率约 26%，16 格墙平均约有 4-5 格特殊格，剩余约 11-12 格为贴纸。

> **v2.5 变化**：厄运格曾在 v2.4 被移出随机墙，现重新纳入每格 roll（5%/5%）。平均每面墙约 1.6 个厄运格。

### 奖品墙类型（9 种）

每个 modifier 既决定墙的特殊规则，也可覆盖墙级参数（如进入金币数）：

| 类型 | 规则 | 备注 |
|------|------|------|
| 🎭 神秘面纱 | 约 30% 贴纸格隐藏，抽相邻格时揭示 | |
| ✨ 双倍惊喜 | 约 20% 格子带 ×2 标记（作用于簇产出） | |
| 🔀 交叉问答 | 行列必须交替选择 | |
| 🎡 转盘中心 | 中心 2×2 每抽一次顺时针旋转；生成时强制中心有炸弹/膨化格 | |
| ➡️ 传送带 | 随机一行/列每抽一次整体前进一格；移动后簇自动重算 | |
| 🌱 野蛮生长 | 抽到某格后 4 邻居变成和被抽中格子同类型 | 簇成员位置已被消除，只覆盖非簇邻居 |
| 💣 爆裂愈合 | 每次抽取后被抽中**那一格**生成一颗新炸弹 | 簇消除时只在原抽中格放炸弹 |
| 🪞 镜花水月 | 左右互为镜像，抽一格镜像同步结算 | 进入金币 3（默认 5）；同簇镜像去重 |
| 🙏 祝福愈合 | 每次抽取后被抽中那一格生成膨化格 | |

**选取方式**：shuffle bag —— 9 元素用完前不重复，跨回合 / 跨天保留。等概率，不再按权重。

> **已移除**：阴阳轮转（v2.5 移除，与簇系统+订单 sticker 多样性配合差）。

### 奖品墙选择（3 选 1 + 揭晓确认）

每回合开始时，玩家从 **3 面候选墙中盲选 1 面**，随后通过揭晓浮层确认进入：

1. **候选卡只展示"基本信息"**：贴纸种类、厄运格 chip、特殊格 chip；**modifier / 关卡名与描述隐藏**（标题显示"❓ 第 N 号墙"）
2. **点击即承诺**：点击卡片后状态机进入 `wall_reveal` phase，弹出黑屏浮层显示 modifier/关卡的图标 + 名称 + 描述
3. **确认进入**：再次点击任意位置进入 `drawing` phase 开始抽墙
4. **无"返回"**：commit-on-click 防止玩家通过轮流点 3 张卡来 peek modifier

### 墙生成时的 modifier 预处理

Modifier-specific 改格逻辑（神秘面纱的 hidden mask、双倍惊喜的 ×2 overlay、转盘中心的 anchor 注入、传送带的 axis/index/direction 随机化）**在候选生成时就已经烘焙到 grid 中**（`finalizeProceduralCandidate`），不再在 `applyWallCandidate` 里延后执行。这样候选卡展示的特殊格统计和实际墙内容严格一致。

## 簇（Cluster）系统

> **v2.5 核心新增**。是这个迭代里最重要的玩法变化。

### 簇的定义

两个相邻的贴纸格（4-连通：上下左右）若 sticker id 相同，就自动属于**同一个簇**。沿连通关系传递闭包，所有互相可达的同 id 贴纸格构成一个簇。

簇是动态的——matrix 是唯一真源，无需在格子上存储 clusterId。代码中 `src/utils/matrixHelpers.js::getClusterMembers(matrix, r, c)` 提供 BFS 计算。

- 不同 id 贴纸不成簇
- 非贴纸格（金币/食材/炸弹/厄运/膨化等）永远不属于任何簇
- 隐藏（hidden）贴纸格仍参与簇计算

### 动态变化

- **传送带 / 转盘**：移动后簇按新邻接重新计算。原本分开的两片同 id 可能合并成大簇
- **野蛮生长**：被消除的簇位置变空，复制到 4 邻居的副本通常在对角，不会立即互连
- **爆裂 / 祝福愈合**：在抽中位置放炸弹 / 膨化格，那一格不再是簇成员

### 整簇消除

抽中簇内任一格时：
1. **整个簇全部从 grid 上移除**
2. 按下方公式产出对应数量的同 id 贴纸进入背包（不是按簇大小 1:1）

### 产出公式（加性叠加）

```
yield = 1
      + Σ (cell.multiplier - 1)      对簇内每个成员
      + Σ buff_field 4-邻接计数       对簇内每个成员
```

- **multiplier**：来自双倍惊喜墙的 ×2 overlay（每个 ×2 成员 +1）
- **膨化邻接**：每条"簇成员 ↔ 膨化格"邻接关系 +1。同一膨化格若同时贴 2 个簇成员则计 2 次

### 举例

| 情况 | 产出 |
|------|------|
| 1-格簇（孤立） | 1 |
| 5-连簇，无 modifier | 1 |
| 5-连簇，1 个 ×2 | 2 |
| 5-连簇，1 个膨化格贴 1 个成员 | 2 |
| 5-连簇，1 个膨化格贴 2 个成员 | 3 |
| 5-连簇，1 个膨化 + 1 个 ×2 | 3 |

### 镜花水月与簇

- 抽中格 + 镜像格在同一簇 → 簇被消除一次，仅产出一份（镜像不加额外 yield）
- 在不同的同 id 簇 → 两个簇分别按各自公式消除并产出

### 视觉表达

- **桥接矩形**：相邻簇成员之间的 6px gap 用 bg 色矩形填充，整簇看起来是一片连贯形状
- **Hover 高亮**：鼠标悬停簇任一成员时，整簇加金色描边
- **飞行 ×N 角标**：当 yield > 1 时，飞向背包的图标带金色 ×N badge

### 设计意图

- 簇是"惩罚性密集成片"机制——大簇看似产量高，实际基础产出仍是 1（除非 modifier 加持）
- 玩家要在"找散单格保 yield"和"用 modifier 把大簇变成 windfall"之间做选择
- 横向移动 modifier（传送带/转盘）因此获得策略价值——可以重排簇结构

## 贴纸系统

贴纸是**局内材料**——只在当场存在，撤离时不保留。共 **20 种**：

```
🏔️ 山   🌊 海   🌾 田   🌲 林   🌤️ 空
🏝️ 岛   🏜️ 沙   ❄️ 雪   🔥 火   ⚡ 电
⭐ 星   🌙 月   🌸 花   🌪️ 风   🌧️ 雨
☀️ 日   🏞️ 河   🌋 岩   🌈 虹   💎 晶
```

**每面墙从全集中随机出现 3-4 种贴纸**（`WALL_STICKER_COUNT: { min: 3, max: 4 }`，`pickWallStickers(STICKER_TYPES, 3, 4)`）。选择不受订单需求约束（v2.4 短暂尝试过"每格按订单 roll"，v2.5 已 revert）。

**用途**：完成订单需提交特定种类和数量的贴纸；提交后从背包消耗。

## 订单系统

### 货架（Bulletin Board）配置

| 字段 | 值 | 含义 |
|------|----|------|
| `bulletinCapacity` | 5 | 货架容量（始终满员） |
| `initialCount` | 5 | 每天开局通过 setup 二选一填满 |
| `REFRESH_CONFIG.initialCharges` | 0 | 每天开局的刷新次数 |
| `REFRESH_CONFIG.maxCharges` | 5 | 刷新次数上限 |

### 订单模板与权重

| 模板 | 难度 | 奖励品质 | 贴纸总数 | 贴纸种类 | 权重 | 选中概率 |
|------|------|---------|---------|---------|------|---------|
| a | easy | ★ | 2 | 1 | 40 | **40%** |
| b | medium | ★★ | 3 | 2 | 30 | **30%** |
| c | hard | ★★★ | 4 | 3 | 20 | **20%** |
| d | extreme | ★★★★ | 6 | 4 | 10 | **10%** |

### 订单生成算法（`generateOrder()`）

1. **按权重选模板**（`pickWeightedTemplate`）
2. **奖励食材**：模板的每个 `rewardTier` 从对应品质的食材池中均匀随机选 1 个食材
3. **贴纸种类**：从 20 种贴纸里整体洗牌，取前 N 种（N = `template.stickerTypes`）
4. **贴纸数量分配**：循环已选种类，前 N-1 种用 `1 + random(0, remaining-(N-i-1)-1)`，最后一种拿剩余——保证每种至少 1 个

### 订单刷新渠道（v2.5 重建）

货架始终满 5 单，由以下三种渠道维持：

| 渠道 | 触发 | 行为 |
|------|------|------|
| **开局 setup** | 每天 `startGame` 后 | 5 次二选一手动构建初始货架 |
| **完成订单自动补单** | 玩家提交订单后 | 系统立刻入队一个二选一事件 |
| **主动刷新** | 点货架顶 🔄 按钮 | 消耗 1 次刷新次数 → 入队一个二选一事件 |

所有事件共享一个 **FIFO 队列**（`incomingQueue`），永不互相覆盖（v2.5 修复了之前的"事件吞掉"bug）。

**刷新次数来源**：抽中 📋 订单格 +1（不再直接生成订单）；上限 5。

### 订单替换（货架已满时）
- 若选候选时货架 < 5 → 直接加入
- 若货架 = 5 → 进入"替换"模式，点击货架某订单替换之

### 订单提交
- 不限时机，不消耗金币
- 背包中备齐所需贴纸即可提交
- 提交后消耗对应贴纸 → 获得奖励食材

## 厄运系统

### 厄运网格（Doom Grid）
- 与奖品墙独立的小型网格，代表累积威胁
- 总格子数 10，初始：1 个"危险" + 9 个空
- **每回合自动 +1 危险**（递增规则未来可能调整）

### 厄运结算
由奖品墙上的**💀 厄运结算格**触发：
1. 光标在厄运网格上随机落 N 次（N = 当前厄运等级）
2. 落在"危险"格 → -1 HP
3. 落在空格 → 无事

### 厄运等级
- 初始 1（每次结算落 1 次）
- 由奖品墙上的**⬆️ 厄运升级格**触发 +1

### 生命值（HP）
- 初始 5（每天/场重置）
- 归零 → 丢失背包全部内容，强制撤离

## 背包系统

- **容量**：15 格（贴纸 + 食材共用）

## 局外：厨房与做菜结算

### 菜品（DISHES）

每天有指定菜品，结构：
```
{
  id, name, nameEn, icon,
  baseline: <基础分>,
  slots: [
    { name: '主料', required: true, rules: [...], defaultMultiplier },
    { name: '底', required: true, rules: [...] },
    ...
  ]
}
```

当日菜品索引：`Math.max(0, dayNumber - 1) % DISHES.length`。

### 槽位匹配规则

每个槽位有 `rules[]`，每条规则形如：
```
{ match: { tag: '肉类' }, multiplier: 1 }
{ match: { id: 'shiitake' }, multiplier: 2 }
```

**匹配算法**（`getSlotMatch`）：
1. `slot.exclude` 命中 → multiplier 0，禁入
2. 评估所有规则，**取最高 multiplier**
3. 无匹配 → 用 `defaultMultiplier`（通常 0.5，代表"勉强能放但效果减半"）
4. 无规则的槽（如"配料"）→ `defaultMultiplier`（通常 1）

**跨槽加成（`crossBonus`）**：
某槽位可声明 `crossBonus: { requireSlot, requireTag, multiplier }`——其它指定槽位放入指定 tag 的食材时，本槽乘数翻倍。例：炖料的跨槽加成需"底"槽位放面包 → 炖料 ×2。

### 评分流程（`scoreDish`）
1. 预扫描所有 `crossBonus` 是否激活
2. 对每个槽位：取食材 × 槽位 multiplier × crossBonus 加成
3. 汇总所有槽位得分 + 菜品 `baseline`
4. 输出最终分数（用作派遣判定的"实际数值"）

## 派遣判定（五维评分）

灵感源自 Dispatch（超英派遣中心）的多边形评分，用作做菜后的最终评分可视化。

### 五个维度
**健康 / 香气 / 口感 / 味道 / 外观**

### 评分机制
- 每道菜的目标用 5 维数值表示，绘制为五边形
- 玩家做菜的实际表现也输出 5 维数值，绘制为另一个多边形（金色填充）
- 一颗小球在**菜品数值（你的多边形）**内随机弹跳
- 落停时检查是否落在**菜品数值与任务要求的重叠区**内：
  - 在重叠区 → **判定成功**
  - 不在 → **判定失败**
- 覆盖率 = 重叠面积 / 你的多边形面积（即概率指示）

### 物理参数（`DispatchJudgment.jsx`）
| 参数 | 值 | 说明 |
|------|----|------|
| 初速 | 3-5 px/帧 | 起步速度 |
| 摩擦 | ×0.994/帧 | 比例摩擦，速度越慢减得越少 |
| 碰撞恢复系数 | 0.94 | 每次撞壁损失约 6% |
| 停止阈值 | 0.12 px/帧 | 约 7 px/秒，肉眼几乎不动时停 |
| 安全超时 | 15 秒 | 兜底 |

> 当前作为**独立工具页面**实装（点头部「派遣」按钮打开），未来与厨房做菜流程接入。

## 人气值系统

- 人气值 = 玩家的"血量" + 经济引擎
- 每天做菜评价影响人气值涨跌（梯度，非二元）
- **正循环**：人气高 → 收入高 → 升级（厨房设备等）→ 做菜更强
- **负循环**：人气低 → 收入低 → 升级慢 → 做菜更难
- 人气值归零 = 游戏失败

代码中存在 `popularity` 状态字段，**具体涨跌公式与初始值仍待最终确定与接线**。
