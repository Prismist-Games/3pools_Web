## 游戏概述

**主题**：人如何与不确定性共处。主角的餐厅濒临倒闭，电视烹饪节目给了他一个翻盘的机会——每天参加节目搜集食材，回家做菜挽救人气值。

**核心张力**：
- 局内（节目）：贴纸需求 vs 厄运风险，行列选择的策略博弈
- 局外（厨房）：做菜评分 → 人气涨跌 → 影响后续天数

**胜利条件**：当前原型阶段沿用 v2 设定——3 场（3 天）累计 ≥ 30 分。终局"评审 Boss"机制规划中。

## 大局结构（Day 循环）

每"天"= 一次节目搜打撤 + 一次回家做菜结算。

```
[Day N 开始]
   │
   ▼
看到今天的菜品要求（菜名 + 槽位结构 + 五维目标）
   │
   ▼
进入节目（局内）
  - 选择奖品墙
  - 抽贴纸 / 完成订单 / 获得食材
  - 决定撤离时机
   │
   ▼
回家做菜（局外）
  - 把食材填入菜品槽位
  - 派遣判定五维评分
  - 人气值涨跌
   │
   ▼
[Day N+1] ── 直到达成胜利条件
```

代码中：`dayNumber` 即天数计数；`expeditionScores` 累积各天得分；`phase` 状态机驱动 `pre_game → wall_choice → drawing → between_turns → restaurant → cook_result → game_over`。

## 局内：节目（奖品墙）

### 奖品墙基本结构

- **大小**：4×4（代码 `MATRIX_CONFIG.gridSize: 4`）
- 每回合一面墙，回合内不补充
- 每次抽取选择**行**或**列**，从该行/列里随机抽中 1 个格子
- 所有内容采用俄罗斯方块式形状（占 1-4 格，多格物品共享 groupId，抽到任意一格获得整体）

### 格子类型（生成顺序）

| 类型 | 来源 | 抽中效果 |
|------|------|----------|
| 💀 厄运结算格 | Phase 1（正态分布） | 触发结算 |
| ⬆️ 厄运升级格 | Phase 1（正态分布） | 厄运等级 +1 |
| 💰 金币格 | Phase 2 · 6% | 获得 1-2 金币 |
| 📋 订单格 | Phase 2 · 4% | 触发候选订单流程 |
| 🎁 食材格 | Phase 2 · 2% | 获得局外食材 |
| 💣 炸弹格 | Phase 2 · 4% | 爆炸摧毁周围 8 格 |
| 贴纸格 | Phase 3（剩余空格） | 获得对应贴纸 |

#### 厄运格生成（Phase 1）
- 总数呈正态分布（Box-Muller 近似）：均值 5，标准差 1.5，范围 1-9
- 结算/升级比例约各占一半（±15% 浮动）

#### 食材格的品质分布
食材格触发时按品质加权随机选食材：

| 品质 | 概率 |
|------|------|
| ★ | 40% |
| ★★ | 30% |
| ★★★ | 20% |
| ★★★★ | 10% |

### 奖品墙类型（5 种）

| 类型 | 权重 | 描述 |
|------|------|------|
| 🎯 经典赛道 | 30 | 标准规则，行列自由选择 |
| 🎭 神秘面纱 | 20 | 部分格子隐藏，抽相邻格揭示 |
| 🌀 乾坤大挪移 | 15 | 每次抽取后剩余格子随机移位 |
| ✨ 双倍惊喜 | 15 | 部分格子效果翻倍（贴纸×2、厄运×2） |
| 🔀 交叉问答 | 20 | 必须行列交替选择 |

> ⚠️ **注**：墙类型已定义且会从 3 选 1 候选展示，但 `generateWall()` 当前未根据 `wallType` 分支具体行为，**视觉/规则的差异化基本未实现**。

### 奖品墙选择
- 每回合开始时，从 **3 面候选墙中选 1 面**（候选墙类型不重复）
- 候选预览：墙类型 + 包含的贴纸种类 + 厄运格数

## 贴纸系统

贴纸是**局内材料**——只在当场存在，撤离时不保留。共 **20 种**：

```
🏔️ 山   🌊 海   🌾 田   🌲 林   🌤️ 空
🏝️ 岛   🏜️ 沙   ❄️ 雪   🔥 火   ⚡ 电
⭐ 星   🌙 月   🌸 花   🌪️ 风   🌧️ 雨
☀️ 日   🏞️ 河   🌋 岩   🌈 虹   💎 晶
```

**每面墙固定出现 3 种贴纸**（`WALL_STICKER_COUNT.min = max = 3`，`pickWallStickers` 默认参数也是 3/3）。

> 历史问题：早期会出现"墙预览显示某贴纸但实际没生成"的情况，原因是放置算法在每个空格里从池子均匀随机选一种，可能完全漏掉某些种类。固定为 3 种后概率从最坏 ~78% 降到 ~24%~47%；如要彻底杜绝需在放置阶段加保底逻辑（未实现）。

**用途**：完成订单需提交特定种类和数量的贴纸；提交后从背包消耗。

## 订单系统

### 货架（Bulletin Board）配置

| 字段 | 值 | 含义 |
|------|----|------|
| `bulletinCapacity` | 5 | 货架最大订单数 |
| `newPerTurn` | 1 | 每回合新增数（实际以 2 选 1 候选形式提供） |
| `initialCount` | 4 | 开局初始订单数 |
| `maxActive` | 3 | 历史字段，v2 现在 bulletinBoard 直接管理订单，已废弃 |

### 订单模板与权重

| 模板 | 难度 | 奖励品质 | 贴纸总数 | 贴纸种类 | 权重 | 选中概率 |
|------|------|---------|---------|---------|------|---------|
| a | easy | ★ | 2 | 1 | 40 | **40%** |
| b | medium | ★★ | 3 | 2 | 30 | **30%** |
| c | hard | ★★★ | 4 | 3 | 20 | **20%** |
| d | extreme | ★★★★ | 6 | 4 | 10 | **10%** |

### 订单生成算法（`generateOrder()`）

1. **按权重选模板**（`pickWeightedTemplate`）
2. **奖励食材**：模板的每个 `rewardTier` 从对应品质的食材池中均匀随机选 1 个食材
3. **贴纸种类**：从 20 种贴纸里整体洗牌，取前 N 种（N = `template.stickerTypes`）
4. **贴纸数量分配**：循环已选种类，前 N-1 种用 `1 + random(0, remaining-(N-i-1)-1)`，最后一种拿剩余——保证每种至少 1 个

### 订单刷新与替换
- **回合结束**自动产生 2 个候选，玩家二选一加入货架
- **货架满（5/5）**时，玩家被要求选哪个老订单换出
- **当前无手动刷新机制**（无花金币重 roll 货架的入口）

### 订单提交
- 不限时机，不消耗金币
- 背包中备齐所需贴纸即可提交
- 提交后消耗对应贴纸 → 获得奖励食材

## 食材系统（局外物品）

食材即"局外物品"——撤离后带回厨房做菜用。

### 食材结构
每个食材定义在 `INGREDIENTS`（约 60+ 项），结构：
```
{ id, icon, name, nameEn, rarity: 1-4, tags: [大类, 小类] }
```

### 食材分类（`tags` 第一项 = 大类）

| 大类 | 小类示例 |
|------|---------|
| 肉类 | 鸡 / 牛 / 猪 / 羊 |
| 海鲜 | 鱼 / 虾 / 贝 / 蟹 |
| 蔬菜 | 青菜 / 根茎 / 水果 / 菌菇 |
| 主食 | 米 / 面 / 豆 / 面包 |
| 调味 | （规划中） |
| 油脂乳品 | （规划中） |

每个小类下当前有 4 个不同品质的具体食材（如 鸡：鸡胸肉★ / 鸡腿肉★★ / 走地鸡肉★★★ / 乌骨鸡肉★★★★）。

### 获取方式
1. **完成订单**（主要）：奖励食材直接进背包
2. **奖品墙食材格**（次要）：2% 出现概率，按品质 40/30/20/10 加权

## 厄运系统

### 厄运网格（Doom Grid）
- 与奖品墙独立的小型网格，代表累积威胁
- 总格子数 10，初始：1 个"危险" + 9 个空
- **每回合自动 +1 危险**（递增规则未来可能调整）

### 厄运结算
由奖品墙上的**💀 厄运结算格**触发：
1. 光标在厄运网格上随机落 N 次（N = 当前厄运等级）
2. 落在"危险"格 → -1 HP
3. 落在空格 → 无事

### 厄运等级
- 初始 1（每次结算落 1 次）
- 由奖品墙上的**⬆️ 厄运升级格**触发 +1

### 生命值（HP）
- 初始 5（每天/场重置）
- 归零 → 丢失背包全部内容，强制撤离

## 背包系统

- **容量**：15 格（贴纸 + 食材共用）
- **物品形状**：俄罗斯方块式（1-4 格）
- **回收**：可批量丢弃，无补偿
- **背包满**：进入待处理队列，玩家逐个决定替换或丢弃

## 局外：厨房与做菜结算

### 菜品（DISHES）

每天有指定菜品，结构：
```
{
  id, name, nameEn, icon,
  baseline: <基础分>,
  slots: [
    { name: '主料', required: true, rules: [...], defaultMultiplier },
    { name: '底', required: true, rules: [...] },
    ...
  ]
}
```

当日菜品索引：`Math.max(0, dayNumber - 1) % DISHES.length`。

### 槽位匹配规则

每个槽位有 `rules[]`，每条规则形如：
```
{ match: { tag: '肉类' }, multiplier: 1 }
{ match: { id: 'shiitake' }, multiplier: 2 }
```

**匹配算法**（`getSlotMatch`）：
1. `slot.exclude` 命中 → multiplier 0，禁入
2. 评估所有规则，**取最高 multiplier**
3. 无匹配 → 用 `defaultMultiplier`（通常 0.5，代表"勉强能放但效果减半"）
4. 无规则的槽（如"配料"）→ `defaultMultiplier`（通常 1）

**跨槽加成（`crossBonus`）**：
某槽位可声明 `crossBonus: { requireSlot, requireTag, multiplier }`——其它指定槽位放入指定 tag 的食材时，本槽乘数翻倍。例：炖料的跨槽加成需"底"槽位放面包 → 炖料 ×2。

### 评分流程（`scoreDish`）
1. 预扫描所有 `crossBonus` 是否激活
2. 对每个槽位：取食材 × 槽位 multiplier × crossBonus 加成
3. 汇总所有槽位得分 + 菜品 `baseline`
4. 输出最终分数（用作派遣判定的"实际数值"）

## 派遣判定（五维评分）

灵感源自 Dispatch（超英派遣中心）的多边形评分，用作做菜后的最终评分可视化。

### 五个维度
**健康 / 香气 / 口感 / 味道 / 外观**

### 评分机制
- 每道菜的目标用 5 维数值表示，绘制为五边形
- 玩家做菜的实际表现也输出 5 维数值，绘制为另一个多边形（金色填充）
- 一颗小球在**菜品数值（你的多边形）**内随机弹跳
- 落停时检查是否落在**菜品数值与任务要求的重叠区**内：
  - 在重叠区 → **判定成功**
  - 不在 → **判定失败**
- 覆盖率 = 重叠面积 / 你的多边形面积（即概率指示）

### 物理参数（`DispatchJudgment.jsx`）
| 参数 | 值 | 说明 |
|------|----|------|
| 初速 | 3-5 px/帧 | 起步速度 |
| 摩擦 | ×0.994/帧 | 比例摩擦，速度越慢减得越少 |
| 碰撞恢复系数 | 0.94 | 每次撞壁损失约 6% |
| 停止阈值 | 0.12 px/帧 | 约 7 px/秒，肉眼几乎不动时停 |
| 安全超时 | 15 秒 | 兜底 |

> 当前作为**独立工具页面**实装（点头部「派遣」按钮打开），未来与厨房做菜流程接入。

## 人气值系统

- 人气值 = 玩家的"血量" + 经济引擎
- 每天做菜评价影响人气值涨跌（梯度，非二元）
- **正循环**：人气高 → 收入高 → 升级（厨房设备等）→ 做菜更强
- **负循环**：人气低 → 收入低 → 升级慢 → 做菜更难
- 人气值归零 = 游戏失败

代码中存在 `popularity` 状态字段，**具体涨跌公式与初始值仍待最终确定与接线**。

## 设计方向（未实现）

以下是已确定方向但尚未实装的设计：

- **终局评审（Boss）**：3 道菜或一个 set 的综合评分
- **贴纸放置保底**：墙生成时确保每种贴纸至少出现一次
- **奖品墙类型差异化**：5 种墙的具体规则差异目前未生效
- **厨房升级系统**：根据人气与收入解锁厨具/设备升级
- **食材连携效果**：食材组合加成
- **客人个性 / 故事**（VA-11 方向）
- **餐厅视觉作为系统锚点**：随状态变化的可见进度
