# 空间奖池系统设计方案

> **状态**: 原型已实现，与订单列表系统合并测试中
> **日期**: 2026-03-23（基于 2026-03-20 分析对话，多轮迭代）
> **来源**: 分析对话 — 从当前词缀/奖池系统的扩展性瓶颈出发，探索空间化方向

---

## 问题诊断

当前奖池系统的扩展瓶颈不在于词缀数量，而在于物品只有名字和品质两个属性，所有词缀本质上都在操纵同样的两个维度。第8个词缀和第7个在本质上没有区别。

## 核心变化

用 **物品地图 + 词条选择 + 固定 2×2 框** 取代当前的 **物品类别 + 词缀奖池**。

---

## 当前实现规则

### 1. 物品地图

- 每次抽奖从 20 个物品中随机选取 **12 个**，排列在 **3×4 网格** 上
- 抽取后**只刷新被 2×2 覆盖的 4 格**（而非整张地图），其余 8 格保持不变
- 可花 **1 金币** 手动刷新整张地图
- 地图上高亮显示订单需要的物品及其品质要求（品质底色+角标）

### 2. 抽取流程

1. 系统提供 **3 个品质效果词条**（互不重复），玩家选一个
2. 用 **固定 2×2 方阵** 在地图上选一个区域
3. 悬停时预览覆盖范围，订单卡片同步高亮匹配的需求
4. 点击确认 → 扣除金币 → 抽取动画 → 物品进入背包
5. 被覆盖的 4 格刷新为新物品 + 3 个词条重新生成

### 3. 品质效果（词条）


| 效果   | 品质规则                       | 附加规则            | 费用  |
| ---- | -------------------------- | --------------- | --- |
| 波动   | 90% Common / 10% Legendary | —               | 1   |
| 稀碎   | 100% Common                | 获得3个物品          | 1   |
| 以旧换新 | 同牺牲品(5%升1级)                | 牺牲物品换不同名物品，绝育传递 | 1   |
| 硬化   | Rare+(67/30/3)             | 物品绝育            | 2   |
| 精准   | 标准概率                       | 抽2个不同名，选1个      | 2   |
| 提纯   | Rare+(67/30/3)             | —               | 3   |


费用 = 词条原始费用（和旧词缀系统一致），不再有形状精度费。

### 4. 抽取动画

四阶段动画反馈：

1. **亮起**（300ms）— 中奖格子放大发光，玩家看清是哪个
2. **飞行**（500ms）— 图标通过 Portal 从格子飞向背包区域
3. **退场**（400ms）— 抽取结算 + 另外 3 格缩小淡出
4. **入场**（350ms）— 4 个新物品弹入

背包中新物品出现时有 fade-in 效果。

### 5. 被移除的元素

- **物品类别**（水果/药物/文具/厨具/电器）作为机制不再存在
- **"有的放矢"词缀**：功能被空间选择取代
- **形状多样性**：经测试后简化为固定 2×2，形状选择移除

---

## 与订单系统的集成

- **订单→地图**：订单需要的物品在地图格子上显示品质底色和角标
- **地图→订单**：hover 框选时，订单卡片高亮匹配的需求物品（通过 hoveredPoolItemNames + hoveredPoolId 机制）
- 需求端使用旧订单列表（3普通+2撤离），供给端使用空间奖池

---

## 实现架构

采用 **虚拟池子** 方案：`handleMapPlace` 从空间覆盖构建一个池子形状的对象，传入现有 `handleDraw` 管线。所有技能逻辑、熵值处理、以旧换新/精准选择模式自动继承。

### 关键文件


| 文件                                      | 职责                            |
| --------------------------------------- | ----------------------------- |
| `src/data/spatialConstants.js`          | 固定 2×2 形状、品质效果配置              |
| `src/utils/spatialPoolHelpers.js`       | 地图生成、框生成、局部刷新、覆盖计算            |
| `src/components/game/ItemMap.jsx`       | 3×4 物品网格 + 放置交互 + 需求高亮 + 抽取动画 |
| `src/components/game/FrameSelector.jsx` | 3 个词条选择卡片（效果名+描述+费用）          |

## 迭代历程

1. **5×4 全展示 + 多形状**：20 个物品全部可见，6 种形状自由放置 → 信息过载，选择过多
2. **固定封闭模板**：关闭 2 行或边缘列 → 出场概率不均（25%–100%）
3. **随机封闭**：随机关 8 格 + 形状合法性验证 → 合法性难以保证
4. **3×4 每抽全部重生**：每抽从 20 中随机选 12 个 → 等概率但无空间记忆
5. **固定 2×2 + 局部刷新**（当前）：形状简化为 2×2，只选词条；抽取后只刷新覆盖的 4 格，地图持久演化
6. **与订单系统合并**：里程碑网格暂时搁置，恢复旧订单列表作为需求端

核心学习：

- 形状多样性增加了复杂度但未增加足够的策略深度 → 简化为固定 2×2
- 局部刷新比全部刷新更好——保留了空间记忆和地图演化感
- 需求端（订单/里程碑）和供给端（奖池）可以独立迭代
